## 1. 产品定位与本轮决策

平台负责**代码写完之后，以一个需求为单位组织多个服务的交付工作**。开发者用 Codex、
Claude Code 或其他工具完成编码；平台接收服务与分支，组织审查、变更准备、审批、执行和核验。
现有 Review 工作台成为其中的专业视图，不再代表整个产品。

用户期望的入口是：

> 我完成了 A 需求，涉及 S1、S2、S3，分支分别是这些。请检查代码，并准备好测试环境需要的配置和 AB。

平台补齐可查询、可推导的信息；人工集中处理业务决策与缺失信息，不再逐个平台抄填。
自然语言可以辅助录入，但最终输入必须成为可查看、可修订的结构化任务。

本提案采用以下边界：

- 第一条业务流程是**需求变更准备**：多服务 Review → 配置/AB 变更计划 → 一次集中确认 → 测试环境执行 → 回读核验。
- 第一轮配置操作仅覆盖明确的新增与更新；AB 先创建或更新**未激活的实验草稿**。删除、生产放量、自动合并和发布不进入首个闭环。
- AB 暂按 A/B 实验管理理解。功能开关与实验可能共用平台，但语义不同，不能把“开关开启”直接等同于“实验放量”。公司实际含义在适配时确认。
- 企业平台通过类型化 Connector 适配。流程模板决定步骤与门禁，Connector 负责平台协议，AI 负责分析与提出建议。
- 首期仍为 loopback 本机试点；不会因加入插件而开放监听地址，也不会把现在的静态认证宣称为企业 IAM。

用户列出的 12 个阶段已覆盖主要生命周期。建议保留这些阶段，在其中补齐下列交付信息与检查点，
而不是继续增加一套平行流程。

| 所属阶段 | 建议补齐的内容 | 平台的产物或动作 |
| --- | --- | --- |
| 需求/技术评审 | 涉及哪些服务、配置、实验、数据库、接口、消息、定时任务；负责人和验收指标 | 一份关联需求的变更清单；未识别的部分明确列为待确认 |
| 技术评审/任务拆分 | 跨服务兼容性、依赖方向、发布顺序、旧版是否可读取新配置 | 服务关系和执行依赖；避免“各服务单独正确，组合后失败” |
| 开发/代码审查 | 准确的源/目标分支、固定提交、CI 结果、依赖与安全扫描证据 | 可追溯的代码快照、Findings、门禁结果 |
| 测试/预发布 | 配置差异、实验互斥/分群/分流规则、测试数据、跨服务集成测试 | 配置与 AB 计划，以及对应验证证据 |
| 上线准备 | 构建产物与提交绑定；DB 迁移、密钥引用、配置生效方式、备份和回退条件 | 版本化变更包、发布依赖图、回退或前向修复方案 |
| 发布/上线后跟踪 | 谁批准、何时执行、灰度停止条件、观察时长、业务指标 | 执行记录、核验结果、是否继续放量的决策依据 |
| 复盘 | 实验到期、临时开关与旧配置清理；误报和漏项反馈 | 有负责人和期限的清理任务、评测候选样例 |

权限、审批、证据、取消和故障恢复贯穿这些阶段。配置可以在部署前准备，也可能只能在部署后生效，
因此最终流程必须表达依赖关系，不能固定成“Review 完就把所有配置和 AB 都打开”。

当前没有需求级聚合、配置 Connector、AB Connector、发布 Connector、持久化审批或 Operation Ledger。
Workspace Prepare 和 Review POST 仍在 HTTP 请求内执行；本次设计不重复开展 Workspace 异步化。
进入持久编排阶段时再把已有准备能力作为 Activity 调用，保留其内部校验和隔离职责。

此前真实 GitLab / Docker / 模型链路和浏览器试点已通过；代表性企业 PR 的正式质量验收仍未完成。
Review 执行成功只表示得到有效结果，既不表示没有缺陷，也不构成自动发布许可。

## 4. 首个完整业务闭环

### 4.1 用户需要提供什么

首次接入由平台管理员登记服务目录、系统连接和允许的环境。开发者每次只填写：

1. 需求名称/编号和必要的验收说明；需求链接是可选引用，首期不自动抓取任意链接。
2. 涉及的服务和源分支；目标分支优先取服务目录默认值，可在授权范围内选择。
3. 目标环境，首期只接受登记的非生产环境。

服务目录一次维护项目 ID、配置 namespace、AB 应用和发布应用的映射；不要求每次重复填写。
如果有授权的需求系统，后续可由 Connector 导入服务列表和验收条件，但保留确认步骤。

### 4.2 系统完成什么

```mermaid
flowchart LR
    A[需求 A：服务与分支] --> B[授权并固定各服务代码快照]
    B --> C[逐服务 Review 与结果汇总]
    B --> D[读取配置和 AB 现状，提取变更候选]
    C --> E[变更包：问题、计划、缺失项、依赖]
    D --> E
    E --> F[补齐必要信息并确认具体变更]
    F --> G[重新校验权限与资源版本]
    G --> H[Connector 写入测试配置和 AB 草稿]
    H --> I[回读核验与交付摘要]
```

示例仅用于说明产品行为，不是对现有测试项目的实际操作计划：

| 服务 | 代码审阅 | 配置候选 | AB 候选 |
| --- | --- | --- | --- |
| S1 | feature/A 相对 main | 新增 `feature_a.enabled=false`，证据来自代码读取点与需求 | 无候选，仍需要覆盖检查 |
| S2 | feature/A-api 相对 release/test | 修改 `feature_a.timeout_ms`；具体值若无依据则待确认 | 无候选 |
| S3 | feature/A-exp 相对 main | 无候选 | 新建实验草稿；分群、指标、互斥组等由需求或模板补齐 |

界面集中展示“系统发现了什么、根据什么、还缺什么、将改到哪里”。确认后由接口执行，不让用户去每个平台重填同一份计划。
需求只涉及代码时，配置/AB 必须有明确的“不涉及”依据或确认；不能因扫描没有找到就自动视为覆盖完成。

完成定义：全部服务代码快照可追溯；Review 已执行且阻断问题已处理或有授权处置；
必要信息齐全；测试环境配置与未激活的实验草稿写入结果已核验；保留操作证据。
界面显示“测试变更准备完成”，不显示“已发布”或“可直接上线”。

## 5. 领域模型与现有 Task 的关系

| 对象 | 职责与关键字段 |
| --- | --- |
| ChangeRequest（需求交付任务） | tenant、需求说明、environment、service selections、version、当前快照/计划引用；是用户看到的顶层任务 |
| ServiceCatalogEntry（服务目录） | tenant + serviceId、代码仓库绑定、默认/允许目标分支、各环境的配置/AB/发布资源绑定、负责人、catalogVersion |
| ChangeSnapshot（不可变输入快照） | revision、catalogVersion、逐服务 sourceBranch/targetBranch、headSha/targetSha/mergeBaseSha、解析时间、inputHash |
| ServiceChange（服务变更项） | 关联 snapshot、serviceId、一个 PR_REVIEW Task 和具体 executionId/Artifact；保存覆盖状态 |
| ChangePlan（版本化变更计划） | snapshotRef、观察到的外部资源版本、Action 列表、依赖、待补信息、review evidence、planHash；修改产生新版本 |
| ProposedAction（动作提案） | operation、目标绑定、类型化 payload、证据、前置条件、风险、验证条件；AI 可以建议，不能自行授权 |
| PendingAction（待授权动作） | 不可变 plan/action hash、审批主体、策略快照、有效期与执行前重验结果 |
| ConnectorOperation（外部操作记录） | operationId、幂等键、目标版本、尝试/回执、UNKNOWN 核对进度、最终状态和证据 |

关系为：`ChangeRequest → 多个 ServiceChange → 各自的现有 PR_REVIEW Task → Workspace / Review / Artifact`。
首期一份快照中，一个服务只选一个源分支；同仓库多服务可以分别关联，暂不做跨服务缓存或执行去重优化。

这是对原架构“Task 作为业务聚合”的明确增量调整：**现阶段保留既有 Task 的单仓库契约，
在上层增加 ChangeRequest 业务聚合**。后续 WorkflowRun 归属 ChangeRequest；子 Task 只承载审阅执行，
不再各自启动一套交付主流程。无需现在把旧 Task 改成多仓库 union，也不建立两套定时器和恢复引擎。
现有 API 和已保存的历史审阅保持可读；未来是否统一命名另作版本化迁移决定。

需求页的“待补信息、待审阅、待确认、执行中、部分完成、待人工核对、准备完成”是聚合展示。
真实状态来源仍是各步骤/操作记录；不能用一个总布尔值掩盖某个服务失败或未知结果。

### 5.1 服务目录与连接配置

逻辑配置示例，字段仅为契约草案：

```json
{
  "serviceId": "S1",
  "catalogVersion": "1",
  "repository": {
    "connectorRef": "gitlab-local",
    "repositoryId": "2",
    "defaultTargetBranch": "master",
    "allowedTargetBranches": ["master", "release/test"]
  },
  "environments": {
    "test": {
      "config": {"connectorRef": "config-test", "resourceRef": "s1/test"},
      "experiment": {"connectorRef": "ab-test", "resourceRef": "s1"}
    }
  }
}
```

目录按租户存储并由可信部署配置加载；上例省略了外层租户容器。`connectorRef` 只指向管理员登记的
实例，Base URL、TLS 信任和凭据引用位于独立私有连接配置。任务不能提交任意 URL、namespace 或
凭据来覆盖目录。目录负责映射，授权策略仍需独立检查；“目录存在”不等于“当前身份可以使用”。
共享 namespace/AB 应用要按**真实资源标识**做冲突检查，不能只按 serviceId 加锁。
资源标识包含连接实例与环境。D1 只复用当前登记的单个 GitLab 实例；未来接入多个实例时，
仓库授权必须升级为 `connectorRef + repositoryId` 的绑定，避免不同实例中同名项目 ID 被当作同一授权对象。

### 5.2 分支输入如何保持可复现

- 授权所有服务/仓库后，再访问 GitLab。分别读取源分支与目标分支的完整 SHA，再用这两个 SHA 计算 merge-base。
- 保存每个服务的解析时间。多个 Git 仓库不能提供全局瞬时原子快照，本平台记录的是明确的一组不可变输入。
- 已成功创建的快照使用同一幂等键重放时直接返回原记录，不重新解析移动中的分支。
- 分支更新后，由用户显式创建新快照；不修改旧 Task、Workspace、Findings。新计划不得拿旧 SHA 的 Review 当作新代码的结论。
- 首期执行确认前重新检查源/目标引用和外部资源版本；发现漂移则要求新快照/计划并使旧批准失效。
  检查不能锁住外部 Git；以后发布必须使用批准的不可变构建产物，不能临时拉取最新分支。

## 6. 插件化设计

### 6.1 三种可替换部分

| 扩展点 | 负责什么 | 示例 |
| --- | --- | --- |
| Workflow Template | 步骤依赖、门禁、何时等待输入/审批、失败处理 | `change-preparation-v1`；以后增加发布和观察模板 |
| Analysis Provider | 读取受控证据，输出结构化分析，不直接操作企业平台 | 现有 Codex Review；配置候选提取；跨服务兼容检查 |
| Connector | 将稳定的业务操作映射到某个平台的 API，处理回执和平台差异 | GitLab；公司配置平台；公司 AB；公司发布系统 |

提示词/Skill 可以改善分析效果，但不是权限或副作用边界。核心流程不出现公司平台的 URL 和字段判断。
首期使用**编译期注册的 Go 接口与适配器**，类似 Java 的接口加实现类；配置选择实例。
不使用 Go 动态 `.so`、任意上传脚本或未审核的远程插件。不建设插件市场或通用拖拽流程编辑器。
只有出现真实部署隔离需求后，再把相同契约搬到独立 Connector 进程。

### 6.2 能力契约

不要用一个接受任意 JSON 和 HTTP 地址的万能 `execute` 接口。不同领域提供窄接口，例如
`RepositoryResolver`、`ConfigReader/ConfigWriter`、`ExperimentReader/DraftWriter`；已有
`review.Runner` 与 Review 应用服务继续复用。以下是语义契约，不是本轮要一次创建的代码清单：

| 操作 | 输入与输出 | 责任 |
| --- | --- | --- |
| DescribeCapabilities | 类型/schema 版本、读写/草稿/CAS/幂等/核对/补偿支持情况 | 缺少所需能力明确阻断，不悄悄降级 |
| Read / Resolve | 已授权的资源绑定 → 当前状态、资源版本、有限证据 | 只读；对响应大小、超时、错误进行约束 |
| Validate | 类型化计划 + 当前状态 → 校验问题、可执行前置条件 | 规则由代码执行；平台原生校验属于 adapter |
| Apply | 已重验授权的动作 + operationId + expectedVersion → 回执或未知结果 | 只能执行计划列明的动作；先有持久操作记录 |
| Verify / Reconcile | operationId/回执/预期状态 → 已达成、未达成、仍未知 | 区分“请求被接收”和“变更已生效” |
| Compensate（可选） | 明确补偿计划 + 执行证据 + 当前版本 → 新操作回执 | 只有 adapter 和策略允许时才能执行 |

平台层统一处理可信租户、动作授权、审批、操作幂等、审计和状态流转；adapter 只实现平台协议及语义映射。
不能让每个插件自行实现一套独立审批和重试策略。

描述信息至少含 `kind`、`contractVersion`、`implementationVersion`、输入/输出 schema 和能力列表。
计划固定这些版本与连接配置版本；插件升级不能悄悄改变已批准 payload 的含义。
平台专有字段使用版本化、严格校验的扩展 schema；不支持的实验分配算法、互斥规则或配置发布语义必须报出差异。

首批实现：GitLab 只读适配器扩展、已有 Review、受控配置参考适配器、受控 AB 草稿参考适配器。
参考适配器通过本机测试 HTTP 服务验证协议与失败处理，不能被称为已接入公司系统。

2026-11-16 接续确认：模型理解是完整目标中的必要能力，literal-calls.v1 不能替代模型分析。
2026-11-17 已接入可选模型候选通路，复用只读 Runtime 并与规则合并；独立契约、证据边界及验证限制见 [模型候选分析](model-candidates.md)。
公司 Skill 用于业务规范和分析方法；MCP 或直接 API 可作为 Connector 的接入方式。
连接/资源映射、权限、计划校验、人工确认、幂等和核验仍由平台负责，分析阶段只读，确认后的写入阶段独立控制。

## 7. 配置和 AB 如何自动准备

### 7.1 信息来源与完整性

按“明确声明 → 平台现状与规则 → 代码分析候选”的顺序形成计划：

1. 需求/服务模板中的已知配置及实验要求；可选的仓库内结构化变更清单。
2. 当前环境配置、类型、namespace、实验定义、平台必填字段和已登记默认值。
3. 固定 diff 和必要的只读上下文，例如新增配置读取点、默认值变化、实验 key 引用。

不是要求开发者必须额外维护一份 YAML；没有清单也可以分析，但代码无法推出的业务值必须待补。
每条候选保存来源引用、相关服务/SHA、当前值或脱敏摘要、期望值、理由和待确认字段。
“代码中找到一个字符串”不足以证明它是配置项，也不足以证明没有其他变更。
跨服务摘要需要关联接口、配置和实验证据；首期逐服务 Review 不能宣称已经完成跨服务兼容性验证。

AI 输出先做 schema 和授权范围检查，再经确定性规则验证。恶意注释、仓库文档或平台返回文本
不能新增连接、扩大目标环境、改变审批策略或直接触发写操作。
候选提取使用独立的版本化输出契约，例如 `change-candidates.v1`，绑定输入快照与证据；
不要把配置写入指令塞进已有 Findings schema。只读分析可以复用现有 Runtime，不需要另造模型循环。

### 7.2 配置语义

- 区分“新增且必须不存在”和“更新且必须匹配已有版本”；更新保留基线，拒绝静默覆盖别人刚修改的值。
- 校验类型、必填值、范围、环境和作用域；相同真实 key 的多服务提案先合并或报冲突。
- 平台的保存草稿、发布配置、应用加载是不同阶段；计划要展示实际影响，回读值成功不等于应用已经加载。
- 密钥只保留受控 `secretRef` 和版本，不进入 diff、模型输入、普通日志或明文 Artifact；回退同样使用受控引用。
- 首期不自动删除；无法安全确认旧值、权限或生效方式时停在待处理状态。

### 7.3 AB 语义

- 分开建模实验定义、变量、分群、互斥、分配规则、指标、生命周期和激活动作。
- 首个闭环只操作未激活草稿。平台必须能明确保证草稿不会分流；**不能用“流量填 0”冒充未激活**。
- 开启实验/调整流量是未来的独立动作，依赖代码部署、配置生效、验证证据和相应批准。
- 同一实验被多个服务引用时使用一个实验动作和多个依赖，不能为每个服务重复创建实验。
- 不同 AB 平台的分桶与互斥语义可能不可等价映射；adapter 要明确支持能力，不能只翻译字段名。

## 8. 执行、审批与恢复

### 8.1 审批绑定具体结果

界面可以一次确认整份计划，但底层按动作形成授权记录。批准绑定：租户、身份、目标环境、服务/实际资源、
snapshot、planHash/actionHash、资源前置版本、策略与插件版本、有效期。计划一旦修改便生成新版本，不能沿用旧批准。

流程为 `PROPOSED → PENDING_APPROVAL → APPROVED → REVALIDATING → READY → CONSUMED`。
批准只记录人的决定；执行前重新检查当前权限、资源版本及绑定项，通过后才形成一次性执行授权。
失配进入 `INVALIDATED`。重验与授权消费在平台事务中记录，adapter 写入还必须使用外部条件更新，
避免“检查完之后别人又改了”的时间窗口。外部系统不支持可靠前置条件且存在并发写者时，首期拒绝自动更新。

本机可以显式配置同一人创建并批准测试动作，记录 self-approval；不宣称实现职责分离。
企业环境再接审批人规则或审批平台。读取仓库的权限不能自动授予配置修改、AB 发布或生产操作权限。

### 8.2 持久化边界与原架构的关系

原始《企业智能体架构设计文档》ADR-004 已选择：只读 Phase 0 不依赖编排器，进入可靠性阶段后采用
**自托管 Temporal**。本方案保留该选择，不在 Go 服务里另造持久定时器、长审批等待和补偿引擎。

实施顺序调整如下：

| 原设计内容 | 本轮处理 |
| --- | --- |
| 企业控制平面 + 类型化 Connector | 保留，具体落到需求变更准备 |
| 单仓库 PR Review 先行 | 已有实现复用为步骤；在其上增加需求级聚合 |
| 可靠性阶段引入 Temporal、事务记录、持久审批 | 保留；是开放真实配置/AB 写入的前提 |
| 第二场景 Bug Fix / 编码代理 | 按用户新方向后移，改以配置/AB 变更准备验证副作用契约 |
| app-server 迁移与完整 AgentSession/Turn | 另行评估；Connector 写入与人工计划批准不依赖迁移，现有只读 exec 可继续使用 |
| 30～50 代表性 PR 与正式质量评测 | 保留为质量工作线；没有完成前不能让模型结论独立放行高风险动作 |

建议可靠性阶段使用 PostgreSQL 存业务记录/审批/Operation Ledger/Outbox，Temporal 保存流程控制历史。
具体部署、版本、Go 驱动和 SDK 在该切片开始时确认；本轮和下一只读切片不引入这些依赖。
Temporal history 只传 ID、版本、hash、状态与 Artifact 引用，不复制代码、配置密文或完整模型正文。
业务记录与 Outbox 在同一数据库事务内提交；调度/信号按稳定事件 ID 去重，并允许对账。
Temporal Activity 的重试不能替代外部操作幂等。

真实外部写入前，必须持久保存快照、计划、批准、幂等键、操作状态和必要证据；普通内存 map、
浏览器 localStorage、散落 JSON 文件或“重启后重放全部动作”不能替代这一能力。

### 8.3 部分失败与未知结果

- 动作使用稳定 operationId，重试不更换；远端支持幂等键时透传。不同 payload 复用同一个键返回冲突。
- 创建 Operation Ledger 与消费一次性授权必须在同一数据库事务完成，事务提交后才开始外部请求。
  写者持有租约与 fencing token，拒绝迟到写者更新本地结果；远端不支持 fencing 时仍依赖其条件更新/幂等与核对，
  不能宣称仅靠本地锁实现了远端 exactly-once。发生超时/断连/进程退出，进入 `UNKNOWN` 或待核对状态。
- 先依据远端回执、幂等键或可证明唯一的资源状态核对，不能把超时当成未执行并直接重写。
  若无法区分“未执行”和“执行后又被别人修改”，转人工核对，不能仅凭当前值不同判断可安全重试。
- S1 成功、S2 失败、S3 尚未执行时，保留每项事实；停止依赖失败项的动作，按模板决定独立项是否继续。
  首期写入采用保守的停止后续策略；读取/Review 可以继续收集其他服务结果。
- 取消停止新增动作，但已发出的请求仍须核对；取消页面等待不等于取消远端操作。
- 不承诺跨配置平台与 AB 平台的原子事务。补偿必须有预先定义的反向计划、版本前置条件和授权；
  别人已改动或操作不可逆时，优先前向修复/人工处置，不能把别人的新值回滚掉。

## 9. 权限与数据边界

继承现有业务 API 默认认证与租户隔离：401 表示身份无效；403 表示显式请求的租户或动作权限不符；
跨租户对象统一不可见并返回 404。新增 Change、目录、计划、批准、操作和证据引用均须检查租户归属。

新增动作权限至少按 `subject + tenant + service/resource + environment + operation` 判断。
首期可用可信静态策略表达，默认不授予写权限；不需要先建设完整 IAM。
读取证据、创建计划、批准计划、执行配置、激活实验分别授权。
新目录中的仓库绑定必须同时满足原仓库白名单，不能成为绕过现有授权的后门。

连接凭据在工作区之外，以现有安全文件方式或未来 Broker 管理；GitLab、配置、AB 分别使用相应服务身份。
只把本次动作所需凭据交给 Connector，模型、浏览器与普通 Workspace 均拿不到。
连接限定 HTTPS、可信 CA、允许目标与受控重定向行为；本机参考服务仅供离线测试，不放宽真实 adapter 的边界。
日志记录 ID、动作、状态、摘要和脱敏错误，不记录 token、完整配置秘密或上游原始响应。

## 10. 交互与 API 草案

D1 的五个端点已落地；下表其余阶段仍为草案。D1 未提前创建子 Task 或配置/AB 接口。

首页转为需求交付列表。打开一个需求后，先看到：目标环境、涉及服务、总体进度、阻断项和下一步。
服务列表包含源/目标分支、快照、Review 状态；详情复用现有 diff/Findings 页面。
“配置”“AB”“执行记录”展示对应结构化内容，优先展示变化和影响，把 SHA/路径等技术信息收起。

操作按钮应与状态一致：固定代码快照、开始审阅、补齐信息、查看变更计划、确认并执行测试变更。
浏览页面、刷新和打开历史记录仍只读，不暗中调用模型或执行平台写入。
“无候选”“明确不涉及”“扫描失败”“尚未分析”必须是四种不同结果。

接口均在现有认证中间件之内；实现状态按阶段区分：

| 阶段 | 接口 | 作用 |
| --- | --- | --- |
| D1 | `GET /api/v1/services` | 当前身份可用服务与环境，隐藏凭据和内部连接细节 |
| D1 | `POST /api/v1/changes`、`GET /api/v1/changes`、`GET /api/v1/changes/{id}` | 创建、列举和读取需求；tenant 取可信上下文 |
| D1 | `POST /api/v1/changes/{id}/snapshots` | 带幂等键和 expectedVersion 固定全部服务输入，不调用模型 |
| D2 | `POST /api/v1/changes/{id}/reviews` | 对指定快照启动子 Review；结果读取沿用执行 ID/Artifact |
| D3 | `POST /api/v1/changes/{id}/plans`、`GET /api/v1/changes/{id}/plans/{planId}` | 生成/读取只读变更计划 |
| D5 | `POST /api/v1/changes/{id}/plans/{planId}/approvals` | 确认不可变计划，要求相应动作权限 |
| D5 | `POST /api/v1/changes/{id}/plans/{planId}/executions` | 幂等执行；执行前再重验，不直接信任批准标志 |

现有 `/api/v1/tasks/*` 保留。新接口不要求前端填写完整 SHA、baseSha、connector URL、
凭据或真实 namespace。D1 的快照解析可以同步只读执行；D2 的首期 Review 仍使用现有同步语义，
只承诺进程内幂等和逐服务结果查询，不承诺关页续跑。持久后台执行在 D4 接入，避免先造一个临时后台队列。

## 11. 分步落地与验收

阶段使用 D1～D6 命名，避免与已有 M14 和开发手册第 1～50 步混淆。
整个首个业务闭环在 D6 验收，D1 不是“配置和 AB 已经完成”。

| 切片 | 交付内容 | 可观察的完成条件 |
| --- | --- | --- |
| **D1：服务目录与需求快照** | 租户范围服务目录；需求创建/列表/详情；按服务+分支固定多仓库引用 | 受控三个项目得出可追溯快照；支持 main/release 等非 master 目标；幂等重放不移动；未知服务/越权先拒绝；不调用模型 |
| **D2：多服务 Review（已实现）** | 创建并关联现有 PR_REVIEW 子 Task；准入/准备/审阅/汇总；前端复用工作台 | 一次发起审阅流程得到逐服务结果；一个失败不丢其他结果；旧快照结果不冒充新结果；人工判断问题处置 |
| **D3：配置/AB 只读计划（首版已实现）** | 窄接口、参考平台、状态读取、候选提取、规则验证、计划预览 | 无需重复填平台字段；展示确切 create/update 与证据；缺失/冲突阻断；AB 只支持草稿；无写请求 |
| D4：可靠执行基础（模拟首版已实现） | PostgreSQL 持久交付包、模拟批准/操作记录/Outbox、Temporal 调度和恢复核对；只产生合成回执 | 批准后重启不丢记录；丢响应/重复投递不重复产生模拟效果；过期/漂移/撤权阻断；原工作台草稿仍在内存 |
| D5：受控写入闭环（Writer 与批准/编排控制层已实现） | 配置新增/更新、AB 草稿写入、核验与明确补偿 | S1 成功 S2 失败等故障可演练；重复执行不重建；未知结果可核对；从创建需求到证据汇总全链路通过 |
| D6：一个真实平台组合 | 适配实际配置平台与 AB 平台的授权测试空间 | 用一项真实需求通过 Review → 确认 → 写入 → 核验；人工对照平台确认结果，记录适配差异 |

真实配置/AB 平台目前未提供，所以 D1～D5 可用参考平台推进；D6 才需要其 API 文档、资源映射、
权限范围和工作区外的凭据引用。首期不使用 UI 自动点击冒充稳定适配器，也不虚构公司 API。
发布系统 Connector、数据库变更、CI 门禁与发布后观察随后扩展，复用同一计划/授权/操作记录路径。

### 必需回归矩阵

- 租户：Change、目录、子 Task、Workspace、Review、Artifact、计划、审批和操作不能跨租户引用；拒绝时无下游写请求。
- 快照：带 `/` 的分支、不同目标分支、分支移动、项目/分支不存在、无共同祖先、并发同键与不同内容冲突。
- Review：单服务失败、重试、旧响应迟到、快照更新、模型无效输出；现有本机试点与历史读取不回归。
- 计划：配置新增/更新、缺值、类型错误、秘密引用、共享 key 冲突、AB 不支持草稿/互斥语义、恶意仓库文本。
- 执行：权限变更、批准过期、版本漂移、成功但响应丢失、重复投递、执行中重启、部分成功、取消与补偿冲突。
- 插件替换：两种受控配置/AB 实现通过相同契约测试；仅调整绑定和 adapter，不改核心流程。

不为这些设计一次性堆空接口或测试；每个切片按现有公共行为测试模式实现。
