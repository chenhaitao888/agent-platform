# D5.4：处置报告与独立配置补偿

2026-11-17。D5.3 已推送为 `430ff01`。本步为已结束或结果未知的写入生成持久处置报告；
能够安全准备的配置恢复进入新的交付包，重新批准后通过原写 Worker 执行。**没有自动回滚，也没有修改常驻试点或公司平台。**
原协议仍见 [参考 Writer](reference-writes.md)、[写入控制层](write-execution.md) 和 [部署入口](write-deployment.md)。

## 支持范围

首版只自动准备 `config.update` 的原值恢复。每项原 Intent 必须与封存计划/动作一致，远端回执必须匹配原请求，
该项必须已有 VERIFIED 核验记录。实际恢复仍使用普通条件更新 Writer；不会新增一个绕过 CAS 的“回滚”接口。

| 原动作/情况 | 处置 |
| --- | --- |
| 已核验的配置更新，当前条件匹配 | 准备独立配置恢复动作 |
| 新增配置、创建实验草稿 | 人工处理；不支持自动删除 |
| 更新实验草稿 | 首版列为人工处理，不自动恢复实验定义 |
| 未发出请求、远端明确拒绝、config.no_change | 无需恢复 |
| UNKNOWN、仍有在途请求或未完成回读 | 先核对原执行，不产生可执行补偿包 |
| 资源后续变化、读契约变化、无法读取或旧值不再合法 | 人工核对或重新准备，不吸收新版本强行恢复 |

原执行 RUNNING/QUEUED 时拒绝准备。没有后台自动扫描、自动补偿或凭平台当前值猜测原请求是否执行的路径。
原执行即使全部成功，也可以由有权限的人明确准备恢复计划；这不代表系统建议撤销业务变更。
不支持对补偿执行继续生成“补偿的补偿”。人工事项没有自动完成登记，报告保留准备时的分类，不能据此声称已整体回滚。

## 资源与证据条件

准备只读取交付数据库和配置 Reader，不调用模型或 Writer.Apply。浏览器不能提交恢复值、Intent、回执或目标。
旧值只取原封存动作的 CurrentValue；敏感值仅使用原有 secretRef/secretVersion，不读取真实密钥。

对每个可恢复资源，要求：

1. 当前 Reader 描述与原计划一致。
2. 当前资源版本等于**原执行在该资源上的最后一个 APPLIED 回执版本**。这允许同一次原执行的多项成功写入推进版本，
   不会把较早回执的资源版本误当成最终版本，也不会采用外部后续修改后的最新版本。
3. 当前条目版本、值摘要和保存语义仍与该项原回执一致。
4. 原值符合当前类型、范围、允许值、CAS 能力和密钥引用登记；复用正常配置计划的规则。

可恢复项按原动作的逆序进入新计划，所有共享资源动作使用准备时的同一资源版本。
执行时仍由 D5.2 的 VERIFIED 前缀推进后续版本，保存确切 Intent 后只发送一次。
在准备与执行之间发生变化会阻断；在重验与远端提交之间发生变化由平台 CAS 拒绝。不会覆盖其他人的后续修改。

代码引用仍绑定原快照；准备可执行补偿和执行前都重新检查 GitLab 引用。代码已经前进时，本版会阻断，
不会自行重写快照或执行代码回退。沿用原 Findings 只是保存审阅证据，**不是对反向业务行为的新质量证明**；
批准者仍须判断原值在当前业务中的适用性。配置发布、应用是否已加载、实验激活均不在本步范围。

## 持久计划与独立批准

迁移 [004_compensation.sql](../backend/internal/delivery/migrations/004_compensation.sql) 新建处置报告表。
报告及可执行补偿交付包在同一事务提交；使用租户级幂等键，并在事务中重查源执行摘要，避免读取期间原结果变化。
同键重放读取原报告，不再次读取平台；新观察必须使用新请求。原计划、原执行与回执不被改写。

报告记录源 bundle/run ID、源包摘要、完整源执行摘要、准备主体/理由、逐项处置和新的类型化 Plan。
报告状态包括 READY_FOR_REVIEW、MANUAL_ONLY、NO_ACTION_NEEDED、BLOCKED。只有 READY_FOR_REVIEW 生成新交付包。
其 PlanHash、包 ID/摘要、批准和操作 ID 均独立；旧批准不能用于新包。

新包 `compensation` 来源字段绑定报告、源包/源执行及人工事项数量。新的批准和每次新派发都会检查这条持久关联。
摘要用于完整性与并发条件检查，不是客户端可持有的授权令牌。结果补证依旧允许在批准撤回后进行，不发起新写入。

沿用 `delivery.write.v1`、事务 Outbox、操作账本及 UNKNOWN 回查，不更改旧工作流历史。
补偿也是有副作用的新执行，会出现部分成功、拒绝或未知；原 D5.2 的停止后续与回查规则同样适用。
重复准备、重复投递、API 回复丢失都不能变成重复恢复；再次准备时若版本已被先前补偿推进，也不会直接采用它继续恢复。

## 权限与 API

无需新增连接文件，沿用已显式启用的 WRITES_FILE。目录新增三个独立权限，默认不会授予：

- `prepare_compensation`：读取并准备原执行的处置报告。
- `approve_compensation`：批准新的补偿交付包。
- `execute_compensation`：发起补偿执行。

这些权限仍需全部相关服务的 `read` 和仓库允许列表。普通 approve_write/execute_write 不能代替补偿权限。
撤回沿用 revoke_write，查询/回查仍需当前读取权限。self-approval 规则按新计划的创建者/封存者检查，默认禁止自批。
例如准备者只授 `read, prepare_compensation`，批准者授 `read, approve_compensation, revoke_write`，执行者授 `read, execute_compensation`。

所有接口在 `/api/v1/deliveries/{deliveryId}` 下：

| 方法与路径 | 作用 |
| --- | --- |
| POST `/write-executions/{executionId}/compensations` | 只读准备并持久保存报告；新建 201、重放 200 |
| GET `/compensations` | 查询该源交付包的历史报告 |
| GET `/compensations/{compensationId}` | 查询单份报告 |

准备 body 只允许 idempotencyKey、expectedExecutionHash、reason 和可选 tenantId。
expectedExecutionHash 取执行 GET 返回的 evidenceHash，不能以公开投影重新计算；服务端摘要包括未公开的原 Intent。
跨租户对象不可见；执行与报告必须属于 URL 中的源包；拒绝主体、恢复值、Plan、Writer、Completed 等额外字段。

打开报告的 derivedBundleId 后，复用该**新包**的 write-approvals/write-executions/revoke/reconcile API。
服务端根据持久补偿来源选择补偿权限；客户端不能通过 mode 字段切换权限，也不能把报告当成批准。

## 页面

原执行下提供“处置与补偿计划”，显式选择已结束的执行、填写理由后准备。
页面同时展示恢复前/后值、无需恢复项、人工项和未知项；打开补偿包后，按钮明确为“批准补偿”“执行配置补偿”。
原代码审阅证据、来源链接与人工项数量持续可见。补偿动作完成仅表示本包的自动恢复动作已经核验，不能当成全部回滚完成。
回复丢失沿用原准备请求键；浏览、刷新、打开报告不会生成新计划或触发外部写入。
