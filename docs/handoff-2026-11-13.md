## 5. 原始 D1 工作约定（已实现，保留作验收依据）

**D1 只做“服务目录 + 需求创建 + 多服务分支快照”，不提前做完整工作流。**
验收体验：输入需求与三个服务的源分支，平台从可信目录查项目与目标分支，展示每个服务的固定版本；无需手填 SHA。
不调用真实模型，不写 GitLab/配置/AB，不启动新的后台队列，不改变本机服务监听范围。

建议按以下次序推进，每次以公共行为测试约束最小实现：

1. 检查当前状态与相关基线测试。先定位目标分支硬编码涉及的 resolver、Handler、测试，避免只改 GitLab URL。
2. 新增 `servicecatalog` 的最小模型与部署加载，按 tenant + serviceId 索引；先采用可信静态配置和受控测试 fixture。
   配置严格校验，未知服务/环境不可用，连接与仓库必须已登记；不开放目录管理 UI。
   D1 只用现有单个 GitLab 实例；不要在仓库授权仍仅按 project ID 判断时开放多个 GitLab 实例。
3. 新增 `change` 聚合的创建、列表、详情及 tenant/version/幂等约束；HTTP 层只做适配，外部解析放应用服务。
4. 新增服务/分支解析入口：目录映射 repositoryId，校验源分支与允许目标分支，先授权全部服务，再读取完整 SHA，计算 merge-base。
   沿用受控 GitLab HTTP 客户端和错误边界，处理带 `/` 的分支和不存在的引用。
5. 新增固定快照动作；建议接口见设计第 10 节。创建需求只保存选择，固定快照才访问 GitLab。
   同一成功快照的幂等重放不重新读分支；相同键不同输入冲突；并发同键不产生多份成功快照。
   部分解析失败不发布一个“完整成功”的快照，保留明确的逐服务错误并可重试；禁止隐式改变已有快照。
6. 旧 `/tasks` 创建仍默认 master，客户端仍不能伪造 target/base SHA；新受信解析路径支持目录配置的非 master 目标。
   后续 D2 从已校验快照创建子 Task，不能再经过旧的 master 解析把已冻结坐标覆盖掉。
7. 最小前端新增需求创建/列表/快照视图，服务来自受权目录，保留旧 Review 入口；不要再次全面改版或预建空白插件页面。
8. 跑相关 Go/前端回归，更新手册和交接，保留改动给用户审阅，不自动提交。

预期新增目录仅供定位，按实际需要创建：`backend/internal/servicecatalog/`、`backend/internal/change/`。
Repository 端口扩展放现有 `internal/repository`，GitLab 实现留在 `internal/connector/gitlab`。
新增 Handler 分文件，避免继续向超长 `handler.go` 堆业务逻辑；不要为此全仓重构。
`CONTEXT.md` 的已实现领域词汇在代码落地时再补正式定义。

### D1 必测行为

- 三个服务可以对应不同仓库与不同目标分支；完整保存源/目标 SHA 与 merge-base。
- 幂等重放期间分支前进仍返回第一次成功快照；显式新快照使用新输入，历史快照不变。
- 并发重复创建、不同内容复用键、expectedVersion 冲突有明确结果。
- 未认证、租户不匹配、跨租户 Change、未授权仓库/服务/环境在访问下游前拒绝。
- 未知分支、缺少共同祖先、单服务解析失败不会显示整体成功，也不创建孤立的 Review Task。
- 旧 master 解析、Workspace/Review 隔离、Artifact 内容授权、前端身份切换/迟到响应/历史结果读取保持通过。

D1 不需公司配置/AB 信息，也不需要新增真实模型调用。后续 D2 接已有 Review，D3 只读计划，
D4 持久化与 Temporal，D5 受控写入，D6 真实测试空间试点；不要把 D1 的完成描述成整个交付 Agent 已完成。
